# Canaries

Automated probes that exercise the full request → *arr push chain for
each major content type. Each canary makes a request via the real
user-facing API (Seerr), then polls Seerr until the request's
`media.externalServiceId` is populated (= Seerr successfully reached
the *arr inside its container netns) and confirms that id matches the
*arr's record.

This forces traversal of the same Docker boundary that the
[reference_ucc-docker-host-loopback] bug class lives on. Earlier
host-side probes (`curl 127.0.0.1:17027/...` from the seedbox shell)
stayed green for ~9h on 2026-05-11 while every Seerr→Radarr request
was failing with `ECONNREFUSED 127.0.0.1:17027` inside Seerr's
container — that's the blind spot this rewrite closes.

The probe is non-destructive: the seed is the lowest-id movie/series
already in the *arr, so Seerr ack's via existing record. The Seerr
request itself is deleted in cleanup; the *arr movie/series is
untouched. On 409 (already-requested), the probe re-uses the existing
request id and skips the cleanup step.

- `library-container-sanity.sh` — whether every payload in the **member-visible** libraries is a container a Plex client can actually open. Added 2026-08-20, the day a **47.6 GB Blu-ray disc image** (`Movies/In the Mouth of Madness (1995)/… BR-DISK.iso`, 47,649,253,376 bytes) landed in Movies and **nothing in the fleet noticed**. Radarr grabbed the release on its **name** — it parses as `Bluray-1080p`, which every profile here allows — the payload was a whole disc, and at import Radarr **re-graded the file to `BR-DISK` and imported it anyway**: the import step does not re-check the profile against the re-graded quality. `BR-DISK` is allowed on **no** profile on this box, so **a quality profile structurally cannot stop this class**. Nothing else could see it either: `hardlink-integrity.sh` asks whether the import *hardlinked*, never whether the imported thing is *playable*; `plex-playback.sh` transcodes the worst-case **selectable** item and an ISO is never selectable, because Plex builds no media part for it; the reaper and `quota.sh` count bytes, and 47.6 GB of unplayable weighs exactly what 47.6 GB of watchable does.
  **Two independent legs, neither subsuming the other.** *Filesystem* — walk `Movies` / `TV Shows` / `Anime` / `Anime Movies` / `Welcome` (never `Music` or `Playlists`, where `.flac` and `.m3u` are correct) and fire on a disc-image extension (`.iso .img .bin .nrg .mdf .mds .cue .vob .ifo .bup` — at **any** size, because a 4 KB `.ifo` proves a DVD rip landed), on a `BDMV` / `VIDEO_TS` / `AUDIO_TS` **directory**, or on the anti-enumeration-gap rule below. *`*arr` grading* — ask radarr / radarr2 / sonarr / sonarr2 what quality they recorded and fire on `BR-DISK` or `Raw-HD`. The second leg is not redundant: Radarr imports a BDMV **folder** by renaming its largest `.m2ts` into the movie directory, which is a playable extension with no disc directory left behind, and only the *arr knows where it came from. The first leg is the only one that sees a file **no *arr owns** — a hand-copied ISO, a manual-import leftover, a `VIDEO_TS` tree an unpack dropped in place.
  **Three whitelists, not one, and a size gate behind them.** Payloads (`.mkv .mp4 .m4v .avi .mov .m2ts .mts .ts .mpg .mpeg .webm .wmv .flv .ogm .divx` — `.m2ts`/`.ts` stay **in**, exactly as in `hardlink-integrity.sh`, because a disc *rip* is caught by the directory rule and dropping a real extension does not tighten a check, it silently removes files from the sample). Sidecars, ignored and counted: subtitles (`.srt .sub .idx .ass .ssa .vtt .smi .sup`), metadata (`.nfo .xml .json`), artwork (`.jpg .jpeg .png .webp .tbn`), text (`.txt .log .md`), plus **any dotfile under the payload size** — `.plexmatch` / `.plexignore` / `.stignore` report *no* extension to `splitext`, and there are 38 of them live. Anything in **none** of the three lists is judged by **size**: under `MIN_PAYLOAD_BYTES` (64 MiB) it is an unwritten-down sidecar shape, **named in the pass line** so the list gets extended deliberately rather than by a red at 04:30; at or above it, it is a payload-sized object nobody listed and it **fires** — which is what lets this catch the *next* unplayable shape rather than only the one that already happened.
  **Vacuity is timed, never green.** `os.walk` swallows `PermissionError` by default, so an unreadable root is indistinguishable from an empty one — an `onerror` handler is passed for exactly that reason. A run that scanned zero payloads **and** graded zero *arr files exits 0 as **inconclusive** and stamps a blind streak in `~/.opt/maint/library-container-sanity/vacuity.json`; past `MAX_VACUOUS_DAYS` (7) the blindness itself is the alert. **Evidence beats vacuity**: findings are evaluated *before* the blind check, so a real ISO in two readable roots is a red even when the other three roots could not be walked. Named paths in `msg=` are ordered by **finding kind**, not discovery order, because `cli.py` truncates at 200 chars and a `container-disc-dir` red that names three unrelated files sends the operator to the wrong place. **daily-0430**, not hourly: the fault is per-title, permanent until an operator acts, and does not cascade, so a whole-library walk plus ~45 *arr calls every hour buys nothing. Exit 0 green / SKIP / inconclusive, **2 red**; Monday-window suppressed by both a wall-clock leg and a **live** window lock. Test overrides: `QFLIX_CANARY_CONTAINER_MEDIA_ROOT` / `_ROOTS` / `_MIN_PAYLOAD_BYTES` / `_DISC_QUALITIES` / `_MAX_VACUOUS_DAYS` / `_STATE_DIR` / `_MAX_NAMED` / `_ARR_TIMEOUT` / `_SKIP_ARR` / `_FORCE_WINDOW`.
- `plex-transcoder.sh`   — Plex `/transcode/sessions` + `/:/prefs` respond <10s with 2xx (catches transcoder daemon stall while main `/identity` still says 200). **API liveness only — it is not a playback test and cannot be made into one by retuning.** Every leg is a GET a healthy HTTP handler satisfies; nothing decodes a frame or moves a byte of transcoded output, so it was green on every tick of the 26-day window in which every movie failed to play for a real member. Kept because it is cheap, runs 3× more often, and separates "the transcode API is wedged" from "the API is fine and the transcoder produces nothing" — see `plex-playback.sh` for the second one.
- `plex-playback.sh`      — whether Plex can actually **produce transcoded video fast enough to play**, which the API probe above structurally cannot see. Picks the library's worst-case movie **at run time** — highest bitrate carrying lossless multichannel audio (TrueHD / DTS-HD MA), i.e. the exact profile that broke — and forces the full software path with `directPlay=0&directStream=0&directStreamAudio=0` at 640x360/720 kbps, so both heavy legs run at once: a video downscale **and** an EasyAudioEncoder downmix to 2-channel AAC. Ten legs, each its own STAGE: `/identity`; section present and non-empty **and the token accepted**; item selectable; the chosen item is **at or above `MIN_TIER`** (default 2); `/video/:/transcode/universal/decision` returns 200 **and** `transcodeDecisionCode=1001` **and** a Part with `decision="transcode"`; `start.m3u8` names a sub-playlist; the sub-playlist lists a `.ts` **and declares an `#EXTINF` duration for it**; `/transcode/sessions` shows **our** session with `videoDecision=transcode` **and** `audioDecision=transcode` **and** `error=0` (a silent direct-stream means the heavy path was never exercised); and then the two legs with teeth.
  **Teeth 1 — bytes, scaled to the playlist, not to a constant.** The first segment must return 200, start with the MPEG-TS sync byte `0x47`, and carry at least `MIN_BYTES_PCT`% (default 25) of `kbps x EXTINF / 8`. The first draft used a flat 32768 bytes, which at 720 kbps is **0.36 s of an 8 s segment** — a transcoder emitting 4.5% of the required output passed. Measured live 2026-08-19: EXTINF 8 s, cap 720 kbps → 720000 B of headroom, actual ~435 KB (60% of cap, because `maxVideoBitrate` is a ceiling), so the 25% floor sits 2.4x below the real value and 5.5x above the old constant.
  **Teeth 2 — throughput, the leg the incident actually needed.** The fault was *"the transcoder never keeps up"*: bytes **were** flowing, just far slower than the 8 s of video each segment represents, so every client rebuffered forever. A byte floor is structurally blind to that. `EXTINF / wall-time` must therefore reach `MIN_RT_PCT`% of realtime (default 80); a live run measures **724–996%**. A curl timeout (code `000`) reports `segment-too-slow`, not `segment-http` — 90 s spent not finishing 8 s of video *is* the throughput fault.
  Finally the session is stopped **and confirmed gone**, **polled up to 5x2 s** rather than sampled once after a fixed sleep: on a loaded shared slot Plex reaps at its own pace, and a single read turns ordinary reaping latency into a fake leak report. A canary that leaks a transcode every 30 minutes on a shared slot becomes the outage it watches for. The ratingKey is **never hardcoded** — qflix-reaper deletes movies on a 60-day add-date rule, so a pinned item becomes a permanent red the day it ages out. Item selection is **client-side over the full listing** because Plex's server-side filters were measured and are not discriminating: `audioCodec=aac` returned all 46 movies and `audioChannels=8` returned all 46, so a server-filtered selector would silently degrade to "the highest-bitrate stereo AC3 file" and reintroduce the blind spot. **Tier degradation is a failure, not a footnote** (fixed in review 2): the first draft printed the tier and passed anyway, so once the reaper aged out every multichannel title the probe would quietly become the cheap-AAC probe it exists to replace, green forever on a test of nothing. The decision call is kept ahead of `start.m3u8` because it is **required**, not decorative — without it `start.m3u8` returned an empty body and the sub-playlist 404'd — and that is also why cleanup is armed **before** the decision curl: `/decision` is the call that registers the resourceSession, so a `decision-*` failure has already created remote state. The segment URI is read from the playlist rather than guessed, because `base/00000.ts` fetched without first GETting `base/index.m3u8` is a 404. Costs one ~8 s segment (0.9–2.0 s wall, ~435 KB) every 30 min and never appears in `/status/sessions`, so Tautulli records no play and no member-visible activity is created. Exit 0 green / **2 red**; suppressed inside the Monday 11:00–15:00 UTC window by both a wall-clock leg and a **live** window lock (a leaked lock whose owner is dead must not mute it forever), reported as a named SKIP. ## Stage labels (failure messages on stderr → Kuma `msg=`)

- `seerr-up-fail` / `radarr-up-fail` / `sonarr2-up-fail` — the named API didn't return 200
- `seed-pick-fail` — a seed exists but its tmdb id couldn't be resolved. NOTE: an **empty but reachable** library (0 movies/series — e.g. the reaper aged out the last title) is treated as an **inconclusive SKIP → PASS** (`PASS: … SKIP: … up but 0 …`), not a failure — it's a content state, not a Seerr→*arr path fault. A genuine *arr outage still trips `*-up-fail` earlier.
- `seerr-push-fail` — POST /api/v1/request returned non-2xx/409 (or 409 with no recoverable id)
- `arr-not-populated` — externalServiceId stayed null after 30s of polling
- `verify-fail` — externalServiceId did not match the *arr's id for the seed
- `cleanup-fail` — DELETE request returned non-2xx (warned to stderr, probe still passes)
- `kometa-config-missing` / `kometa-config-parse-fail` — kometa-libraries / kometa-deploy-drift: can't read/parse config.yml
- `plex-up-fail` / `plex-libraries-fetch-fail` — kometa-libraries: Plex API unreachable or no library list
- `library-drift` — kometa-libraries: at least one kometa-configured library doesn't exist in Plex
- `install-script-parse-fail` — kometa-deploy-drift: can't read the install script's library list
- `deploy-drift` — kometa-deploy-drift: deployed config's library set differs from what scripts/configure/55-kometa-install.sh would render
- `log-stale` / `log-missing-<app>` — stale-log-watchdog: a timer-driven app's log file mtime exceeds its expected cadence, or the log is missing entirely
- `library-empty` / `qbit-no-completed` / `hardlink-regression` — hardlink-integrity: no scanable videos under the media roots; qBit reports completed torrents but **not one content path exists on disk** (data dir nuked / mount gone). The wording is load-bearing: "none resolve to on-disk **files**" conflated *path missing* with *path present but not classifiable as a hardlink*, and that conflation produced the false red of 2026-08-19; or copy-mode imports (`detached`) exceed `MAX_DETACHED`n **and** `MAX_DETACHED_PCT`% over the orphan-excluded sample
- `bazarr-profile-dangling` / `bazarr-profile-unset` / `bazarr-no-languages` / `bazarr-ingest-stalled` —
  `bazarr-ingest.sh`: the instance's configured default profile does not exist in its DB (every
  insert will FK-fail), a default is enabled with no profile id at all, no language is enabled so
  nothing can be subtitled, or the *arr holds items the Bazarr side holds none of. Exit 2 covers the
  cases where the canary asserted **nothing**: `bazarr-db-unreadable`, `bazarr-config-unreadable`,
  `bazarr-db-query-fail`, and `bazarr-ingest-inconclusive` (an *arr could not be reached, so
  "nothing is missing" would be trivially true). A fired predicate outranks an inconclusive leg —
  proving something is broken reports exit 1 even when another probe could not be evaluated.
- `plex-up-fail` / `transcode-api-fail` / `prefs-api-fail` — plex-transcoder: Plex /identity non-200, or transcode/prefs endpoint hung or non-200
- `container-disc-image` / `container-disc-dir` / `arr-disc-quality` / `container-unknown-payload` / `container-blind` — library-container-sanity, reported **most-specific-first** so an ISO never hides behind a generic label. `container-disc-image` is the 2026-08-20 label: a disc image or one of its index files (`.ifo`/`.bup`/`.cue`) is sitting in a member library. `container-disc-dir` means a whole `BDMV`/`VIDEO_TS` structure was imported — the payload inside it is `.m2ts`, which the extension leg passes and **must** keep passing, so this is the only leg that can see it. `arr-disc-quality` fires when the *arr itself recorded `BR-DISK`/`Raw-HD`, which is the folder-import case where the filename looks perfect; it carries a `/missing` suffix when the recorded path is no longer on disk, because a stale disc grading **survives the file being replaced** (seen live hours after the 2026-08-20 incident, when the `.iso` was remuxed to `.mkv` and Radarr went on holding the `BR-DISK` record) and the remedy there is an *arr rescan, not a delete. Tagged rather than suppressed — suppressing it would let a stale disc grading sit unnoticed, which is the failure this canary exists for. `container-unknown-payload` is the anti-enumeration-gap leg: payload-sized, extension on none of the three lists (including *no* extension). `container-blind` is the vacuity clock — nothing has been examined for `MAX_VACUOUS_DAYS`, i.e. the guard stopped guarding; an empty library or an unreadable root passes as a named **inconclusive** until that budget runs out, and never as a green.
- `plex-secret-missing` / `plex-up-fail` / `plex-auth-fail` / `section-missing` / `library-empty` / `item-select-fail` / `tier-below-minimum` / `decision-http` / `decision-refused` / `decision-not-transcode` / `hls-start-fail` / `hls-playlist-fail` / `session-missing` / `session-not-transcoding` / `session-error` / `segment-http` / `segment-empty` / `segment-not-mpegts` / `segment-too-slow` / `session-leak` — plex-playback, one per leg. Four worth reading twice: **`segment-too-slow`** is the label the 26-day outage would have carried — bytes flowed and playback still failed, which no byte count can express. **`segment-empty`** is its sibling, and its floor is now derived from the playlist's own `#EXTINF` rather than a flat 32768 that a transcoder at 4.5% output could satisfy. **`plex-auth-fail`** is separated from `item-select-fail` because an expired `~/secrets/plex.token` used to surface as `sections-unreadable-HTTPError`, which reads as a broken library and sends the operator to entirely the wrong place. **`decision-http`** means *our request or their handler*, never "the item is bad" — a bare 400 is exactly what a probe missing the client-profile parameter set gets back, which is how an earlier malformed probe misdiagnosed a known-good title. `tier-below-minimum` and `session-leak` are the two anti-rot labels: the first refuses to let the probe decay into the cheap-AAC test it replaced, the second refuses to let it become the outage it watches.
- `dash-*` — dash-asset-integrity: the served shell references an asset the running server will not serve, or the document's advertised `Content-Length` disagrees with the bytes delivered. The two faults carry **distinct** labels because they need different responses: a 404 whose file is present on disk is a stale in-process sirv manifest (restartable), a 404 whose file is absent is a partial deploy (not restartable), a 200 whose body never arrives is a stalled worker (not restartable), and the self-heal has its own labels for suppressed-by-the-Monday-window, refused-by-the-24h-breaker, refused-because-the-breaker-latch-will-not-persist, refused-because-the-unit-just-started, and issued-but-re-verification-still-failing. The script header carries the authoritative label table and the `QFLIX_CANARY_DASH_*` env overrides — read it there rather than duplicating the strings here, since this canary is the one that *acts*.
- `digest-stale` / `digest-missing` / `digest-malformed` / `digest-empty` — newsletter-digest-stale: the digest branch's `week_of` isn't fresh at Monday send time, the file/branch 404s or is absent, the JSON fails to parse (or `week_of` is missing/non-string), or `html` is blank. Only evaluated inside the Monday 14:15-24:00 UTC send window — outside it, and on a pure transport failure after 3 retries, the canary passes (`not-in-eval-window` / `digest-check-inconclusive`) rather than alerting.

- `timer-missing` / `timer-inactive` / `timer-stuck` / `timer-read-fail` — `timer-liveness.sh`: a job
  declared in `manifest/jobs.yaml` is not installed on the box, is loaded but not active (it will
  never fire again), or is active with nothing scheduled on either clock. `timer-read-fail` means
  the ledger or systemd could not be read at all. A last run that exited non-success is reported as
  `PASS-WARN`, not a failure — a canary legitimately exits non-zero to report ITS subject down, and
  that already has its own monitor. Jobs whose intended terminal state is "gone" opt out with
  `may_be_absent: true` in the ledger.

- `prowlarr-appsync-missing` / `prowlarr-appsync-magnet-pref-off` — `prowlarr-app-sync.sh`: an
  indexer Prowlarr intends to sync (enabled **and** tag-intersecting **and** category-intersecting)
  is not present in that *arr, or a diagnosed indexer still prefers the proxy download URL over its
  magnet. Both are exit 1. The BROKEN set is exit 2 and each names its stage:
  `prowlarr-appsync-no-apps` (zero applications — "nothing is missing" would be trivially true),
  `prowlarr-appsync-no-indexers`, `prowlarr-appsync-prowlarr-down`, `prowlarr-appsync-arr-down`,
  `prowlarr-appsync-unknown-app`, `prowlarr-appsync-config-missing`, `prowlarr-appsync-probe-error`.
- `plex-unmatched-stuck` — `plex-unmatched.sh`: at least one Plex episode has sat on a `local://`
  guid past the grace window. Exit 2 covers the cases where the canary asserted **nothing**:
  `plex-sections-unreachable` / `plex-section-unreachable` (Plex or a section did not answer),
  `plex-no-show-sections` (nothing to scan — an empty section list is not a clean library),
  `plex-section-truncated` (a section declared `totalSize`>0 and handed back no `Metadata`, i.e.
  empty-because-broken wearing empty-because-clean's clothes), `plex-unmatched-config-missing`.
  A clean run prints `plex-unmatched-clean` and always reports the suppressed sub-grace count.
- `rea-not-auditing` / `rea-unreached` / `rea-verdict-stale` — `rea-liveness.sh`: the workstation
  audit's last run failed, it has not reached the box inside the 336 h cap, or it is still reaching
  the box while its last verdict has frozen (the wedge a heartbeat-only signal cannot see). Exit 2
  is reserved for "this canary cannot assert anything": `rea-heartbeat-absent` (the writer half is
  not wired in `qflix-rea.ps1` — nothing is watching REA, said out loud rather than passed over),
  `rea-heartbeat-empty` / `rea-heartbeat-malformed` / `rea-heartbeat-unreadable`, and any outcome
  token the canary does not recognise, because a watchdog that green-lights vocabulary it does not
  understand is not a watchdog.

## Exit codes

- `deploy-drift` / `deploy-orphan` / `src-missing` / `fetch-failed` — `deploy-drift.sh`: a
  deployed file under `~/scripts` differs from `origin/master`, or exists on the box with no
  counterpart in git at all. The second direction is the sharper one: an unfinished
  decommission, or code running with no source of truth. `fetch-failed` is reported rather
  than passed, because comparing against a stale ref makes everything look clean — which is
  the exact failure this canary exists to prevent.
- 0 — pass; stdout has the `PASS: ...` line (or, for newsletter-digest-stale, `digest-fresh ...` / `not-in-eval-window ...` / `digest-check-inconclusive ...`) that Kuma stores as `msg=`
- non-zero — fail; stderr's `STAGE=... msg=...` line becomes Kuma `msg=`

- `stream-cap-liveness.sh` — whether the two **crontab** entries that enforce the per-member concurrent-stream cap (`kill_stream.sh --max 4` and `stream_stats.sh`, both every minute) are still running. `kill_stream` is member-facing *enforcement* and had **no dead-man of any kind**: not among the Kuma monitors, not among the push tokens, no self-push in either script, and structurally unreachable by the C-01 ledger — whose boundary is systemd timers plus (since 2026-08-06) declared installer units, while **crontab is a third scheduling plane neither leg enumerates**. The only freshness assertion in the repo lived inside `smoke-test.sh`, which no timer runs. If the crontab is dropped by a slot rebuild (`59a-plex-stream-crons-install.sh` records that this already happened once), or the plexapi venv breaks, or `plex.token` expires, the cap simply stops applying and nothing goes red. **Detect-only, and deliberately not a push bolted onto `kill_stream.sh`** — that edits the enforcement path, where a bug does not merely mis-report but can stop the cap working or wedge a per-minute cron; a separate observer can only ever mis-report, which is the failure mode you want there. The clock is the **writer-stamped `ts` embedded in each artefact**, never the file mtime: mtime-freshness is a named defect class here (C-04, discovered 2026-07-25) and both artefacts carry their own epoch, so the content clock is available. `kill-history.json` is appended on **every** run, not only on kills (`kill_stream.py:76-77`), so it is a true liveness signal — verified by sampling both files 75 s apart and watching each advance by exactly 60 s. **Privacy is load-bearing, not incidental**: `state.json` holds member Plex usernames, what they are watching, and per-user counts, so this canary parses *only* the numeric `ts` fields and emits *only* ages — never a username, title, per-user count, or even the total active-stream count, because a Kuma `msg=` is a durable forwarded string and a stream count is consumption. Threshold 900 s tolerates ~14 consecutive `flock` skips on a contended box while still catching a dead cron inside a quarter hour. Exit 0 / 1 `stream-cap-stats-stale` \| `stream-cap-kill-stale` / **2 could-not-assert**. Override: `QFLIX_CANARY_STREAMCAP_DIR`, `QFLIX_CANARY_STREAMCAP_MAX_AGE_S`.

- `cron-liveness.sh` — whether the live **crontab** matches `manifest/jobs.yaml`, in **both** directions. QFlix schedules work on three planes — repo-tracked systemd timers (`timer:`), installer-generated timers (`unit:`, covered 2026-08-06), and the user crontab — and the third was the last one outside the dead-man boundary. It was not merely unmonitored but *inexpressible*: a crontab line has no unit name **and** no file in git, so neither existing field could name one, leaving all ten lines unadjudicated and unadjudicat**able** — including `kill_stream.sh --max 4`, which is member-facing enforcement of the per-member concurrent-stream cap. `cron:` entries now declare them, and this is the LIVE half of that: the offline C-01 detector reads the declarations and demands a written dead-man answer for each, but it runs against git and cannot see the box, so it can never notice a line that was **dropped** (`59a-plex-stream-crons-install.sh` records that a slot rebuild already wiped these once, silently) or one **added** without adjudication. `cron-declared-missing` catches the first; `cron-unclaimed` catches the second — and that second direction is what catches the *next* hand-added cron before it becomes another invisible member-facing dependency. Matching is on the `cron:` command substring **only, never on `schedule:`** — that field is documentation, and if it drifted from the real crontab expression this check would start failing for a cosmetic reason. Comments, blanks and `VAR=` assignments are configuration rather than scheduled work, so they are skipped, counted and named. Exit 0 / 1 / **2 could-not-assert**, and that includes the case where the ledger declares **zero** cron jobs: an empty declaration set would make "everything declared is present" vacuously true, which is the empty-because-broken-reads-as-clean trap this repo keeps closing. Deliberately its own canary rather than a leg of `timer-liveness.sh` — different mechanism, different failure vocabulary (loaded/active/next-fire has no crontab analogue), independently swappable, the same reasoning that made `prowlarr-app-sync` a second canary rather than a third probe.

- `tdarr-transcode-error.sh` — whether anything is **parked in Tdarr's terminal `Transcode error` state** beyond the janitor's chance to fix it. That state is terminal — Tdarr never retries it — and nothing reported the population: **13 episodes of one series sat parked from 2026-08-06 until a human went looking on 2026-08-08** (root cause: an unmappable `codec_name=unknown` placeholder subtitle stream aborting the matroska muxer with `Subtitle codec 0 is not supported`). The unknown-codec janitor (daily 04:00 UTC, "QFlix Unknown Codec Stream") now fixes *that* cause; this canary watches the **state**, so the next cause nobody has thought of — a new release group's container quirk, a Tdarr upgrade regression, a broken flow edit (one of those broke 18 episodes for ~7 minutes the same night) — surfaces as a red instead of as a member asking where their episode's direct-play audio went. Same reasoning as `unstick-rate`: a guard on the rule catches only the failure it was written for; the terminal outcome catches every cause. **48h grace = two janitor passes** — a fresh error is expected transient (the janitor sweeps nightly and live-requeues), and alerting on arrival would red every night and train the operator to ignore it; anything older than two passes is by definition a cause the janitor does not handle, which is exactly the population worth naming. The clock is the FileJSONDB record's **mtime — an acknowledged C-04 tradeoff**: Tdarr rewrites the record on state change so mtime is a writer-driven clock, the records carry no reliable transition timestamp to prefer, and the failure direction is safe (a spurious rewrite resets the age and delays an alert one window; it can never fabricate one). Zero FileJSONDB records exits **2**, not 0: this Tdarr holds ~1,500 file records, so an empty scan means the DB moved or the glob broke — empty-because-broken must never read as empty-because-clean. Exit 0 / 1 `tdarr-transcode-error-parked` / **2 could-not-assert** (`tdarr-filedb-empty` \| `tdarr-filedb-unreadable`). Override: `QFLIX_CANARY_TDARR_TERR_GRACE_H`.

- `tdarr-transcode-stall.sh` — whether Tdarr is **transcoding at all**, as opposed to being switched on. Sibling of `tdarr-transcode-error.sh` and deliberately a separate monitor: that one watches the terminal **error** population, this one watches whether work is **happening**. The gap was found the hard way on **2026-08-23**. After a routine `systemctl --user restart tdarr-server tdarr-node`, every transcode worker died the instant it received a job — `EACCES: permission denied, mkdir '/tdarr-workDir-node-…'`, because three libraries carried `cache: ""` and Tdarr concatenates that into an **absolute path at the filesystem root**, which a rootless slot cannot create. The node pruned the worker and never retried. **Nothing saw it**: a file whose worker dies never reaches `Transcode error` — it stays `Queued` — so `tdarr-transcode-error` correctly reported 0 parked; health checks run a different code path and kept passing, so `tdarr-healthcheck` stayed green; the worker **cap** was intact, so `tdarr-throttle-integrity` stayed green; the unit and the node registration were both fine, so `Tdarr` and `Tdarr Node` stayed green. **76/76 green, pipeline stone dead.** Predicate: backlog non-empty **and** a node registered, unpaused and with transcode capacity **and** **zero** busy transcode workers **and** no terminal transcode verdict in `STALL_HOURS` (default 3). The busy-worker condition is what makes it armable — a 5 GB feature legitimately holds a worker for hours without moving the completion count, and a canary that reds on long jobs gets muted inside a week; **in-flight work is proof of life**, idle workers with a queue and no completions is not slow, it is stopped. Ghost records are excluded from the backlog, and only when their **directory was readable** — absence and unreadability are the same `os.path.exists()` answer and want opposite verdicts, so an unmounted media tree can never empty the backlog into a false green (`-unreachable=N` is reported instead). Exit 0 / 1 `tdarr-transcode-stalled` / **2 could-not-assert** (`tdarr-ts-server-unreachable` \| `tdarr-ts-no-nodes` \| `tdarr-ts-filedb-empty`). Overrides: `QFLIX_CANARY_TDARR_TS_STALL_HOURS`, `QFLIX_CANARY_TDARR_TS_DB`, `QFLIX_CANARY_TDARR_TS_STATE`.

- `entitlement-service.sh` — whether the **entitlement API the access gate reads** is alive, authenticated *both ways*, honouring its response contract, and has **ever actually carried a real success through the money path**. `manitoba-maint-entitlement` already has a dead-man ("QFlix Entitlement Gate", 15-minute timer with a 1h heartbeat override), but that watches the *gate*, and the gate is built so a broken *service* is invisible from it: `lib/entitlement.py` grades every outage, every 401, every 5xx and every malformed body as **UNKNOWN**, and UNKNOWN neither grants nor revokes. That asymmetry is the load-bearing safety property of the whole design — an entitlement API outage must **freeze** this system, never **drain** it — but its consequence is a gate that keeps running, keeps pushing green every 15 minutes, and quietly stops provisioning anybody. **Frozen is the safe direction, not a safe state**: a frozen gate means paying members are never granted access, and nobody writes in to report the access they did not get. Five legs, escalating: `/healthz` returns 200; an **unauthenticated** lookup must 401/403 (added 2026-08-07 — if the service ever fails open here, entitlement status for any address is readable with no key at all, a PII exposure with no local change to blame); an **authenticated** lookup does not 401/403 (a rotated key is otherwise indistinguishable from an outage, and would send the operator to restart a service that was never broken); the 200 body is a JSON object carrying a **boolean** `entitled` (the client already refuses to grade a 200 without it — "a contract violation, not a no" — precisely so a server-side refactor cannot silently revoke everybody, and that refusal is correct *and* silent); and the **payer oracle** — `lib/payer_oracle.judge()`, the single implementation of the SPEC section 3 verdict table, delegated to via `qflix-entitlement.py --oracle-check` rather than re-implemented in bash. The oracle answers "has the money path *ever* demonstrated a real success", layering a declared-payer settle clock, a bulk cross-check (`GET /v1/entitlements`, once the operator grants the `bulk` scope) and a forgotten-patron check (fires on **any** ever-entitled account now reading `reason=unknown`, not only when every one is lost at once) into one verdict. Today it is **red from the first run** (`UNPROVEN_BLIND`) and correctly so — the money path has never worked and cannot yet be cross-checked. Legs 2–4 probe a synthetic **RFC 2606 `.invalid`** address so no member address enters a public repo, a Kuma `msg=`, or journald; the oracle leg masks every real address before it can leave the process. Exit 0 / 1 `ent-service-down` \| `ent-auth-not-enforced` \| `ent-key-rejected` \| `ent-lookup-http` \| `ent-contract-violation` \| `ent-oracle-red` / **2 could-not-assert**.

- `unstick-rate.sh` — whether the **autonomous unstick has gone haywire**. `qflix-collect.py`'s `act_on_candidates()` calls `unstick.py`, which does `DELETE /queue/{id}?removeFromClient=true&blocklist=true` — deleting the download, removing it from the client, **and blocklisting the release so the *arr will not grab it again**. It is the most destructive autonomous action on this stack, it is member-facing (a blocklisted release is content that does not arrive), and on 2026-08-07 it destroyed **ten legitimate releases in one run** with no alert, no Kuma red, and nothing anywhere for the operator to see — the only thing that stopped it at ten was `MAX_ACTIONS_PER_DAY`, and that cap resets at 00:00 UTC. **Deliberately watches the ACTION, not the rule**: a guard on the rule catches only the failure it was written for, whereas watching the destructive outcome catches every cause, including ones nobody has thought of. Reads the durable audit trail the actor already writes (`~/.opt/qflix-collect/events/YYYY-MM-DD.jsonl`, one JSON line per action). WARN at 3 actions/day, FAIL at 5, and **always** on reaching the daily cap — hitting the cap means the system wanted to do *more* than it was allowed, which is precisely what a runaway rule looks like. Cap-reached is tested **separately from the numeric threshold on purpose**: the cap is operator-tunable, so raising it must not silently raise the alarm with it (verified — with the cap at 50, ten actions still fails on `rate-high`). Not "alert on any action": unstick exists to act unattended, and a canary that reds on every legitimate use gets muted, which would leave this exactly as blind as it was before. Exit 0 / 1 `unstick-rate-high` \| `unstick-cap-reached` / **2 could-not-assert** — a missing events dir or a single unparseable line exits 2 rather than undercounting, because silence was mistaken for health here once already. Overrides: `QFLIX_CANARY_UNSTICK_WARN`, `QFLIX_CANARY_UNSTICK_FAIL`, `QFLIX_CANARY_UNSTICK_EVENTS`.
