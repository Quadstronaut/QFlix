1Getting started

First time landing on QFlix? Start here.

What is QFlix? #

QFlix is a private media server running on a single Ultra.cc shared seedbox. You watch movies, TV and anime through it. One operator runs the whole thing; everything else (download, transcode, organize, metadata, deletion, alerts, newsletter) is automated.

Front door for users: Plex for video, Seerr for requests. That's it — you don't need to know about the dozen other apps holding it up.

How do I sign in? #

  1. Get a Plex invite from the operator (one-time; you'll see the library appear in your Plex apps).
  2. Plex: open app.plex.tv or any Plex app. Sign in with the same email you got the invite for.
  3. Seerr (requests): open seerr and click Sign in with Plex. Same Plex account — no separate password.
Heads-up: the first sign-in into Seerr may take 10–20 seconds while it links to your Plex profile. Don't refresh — give it a beat.

2Requesting media

The Seerr flow — what works, what doesn't, and how anime routing actually behaves.

How do I request a movie or show? #

  1. Open Seerr.
  2. Search the title, click Request.
  3. For TV: pick seasons (or “All seasons”).
  4. Done. Seerr hands it to Sonarr / Radarr, which searches Prowlarr and grabs the best release — either via qBittorrent (torrents) or SABnzbd (Usenet), depending on which download client the *arr's delay profile prefers. Both are wired up and active.
How long? Popular catalogue items show up in Plex within minutes. Obscure stuff: hours. Brand-new releases: whenever a public/private tracker or Usenet indexer has it.

I requested anime — why didn't it go to the “Anime” server? #

Seerr has four backend servers configured: Sonarr Cinema, Sonarr Anime, Radarr Cinema, Radarr Anime. The Cinema ones are the default. Per the Seerr docs, the only routing axes the API understands are isDefault and is4k — there is no cross-server “anime” genre flag.

So: for anime, expand Advanced on the request panel and pick Sonarr Anime / Radarr Anime from the server dropdown before clicking Request. Otherwise it lands in the Cinema server.

Common screw-up: hitting Request fast without expanding Advanced. The episode files will still show up, just in the wrong library and with non-anime release-naming rules.

My request says “Pending” — what's it waiting for? #

One of three things:

  1. Approval. Seerr is set to auto-approve trusted Plex users but unknown / new accounts can land in a manual queue. Ping the operator.
  2. No grab yet. Sonarr / Radarr is searching but trackers have nothing matching the quality profile. The next scheduled re-search picks it up. Anime / obscure foreign releases can take days.
  3. The *arr server didn't get it. Rare. If it's been hours and Tautulli shows the title isn't even queued, ping the operator — usually the *arr restart at the next maintenance window fixes it.

The file is there but it's broken — wrong audio, missing subs, etc. #

Don't request the title again — that won't replace what's there. Use Seerr's Report Issue button on the title page. Categories: Video, Audio, Subtitles, Other. The operator sees these in the Seerr inbox and either re-grabs the file, or Bazarr re-fetches subs, or Tdarr re-transcodes.

Seerr can't find the title I want #

Seerr only knows about titles that exist in TheMovieDB (TMDB). If TMDB has it, Seerr finds it. If not — usually rare foreign films, fan-edits, very-very-new releases — the operator can add it to Sonarr / Radarr directly. Ping them with the title + year + IMDB or TMDB link if you can find one.

3Watching

Plex playback problems and how to recover.

Plex keeps buffering / pausing to “Direct stream” #

Usually one of these:

  • Your connection. Test your download speed. 4K HEVC needs ~25 Mbps sustained; HD ~6 Mbps.
  • Transcoding tax. If your client can't direct-play the file (wrong codec, wrong container, subtitles burned in), Plex transcodes — and this server has a shared CPU. Try setting Quality to the original resolution but a lower bitrate, or use a client that direct-plays more formats (Plex desktop, Apple TV).
  • Stream-cap. Each member may run up to 4 concurrent streams; a kill-stream cron (Plex Pass feature) enforces it per-member, not as a server-wide total. Start a 5th stream yourself and one of your own streams gets killed within 60 seconds — other members are never affected.

Plex says “Server unavailable” #

  1. Open status.plex.tv — Plex's own service goes down a few times a year.
  2. Check the QFlix Uptime Kuma status page. If Plex is red there, the operator has been pinged already and it's auto-healing.
  3. Force-quit your Plex client and reopen. SSO tokens occasionally need a kick.
Self-heal: if Plex is down, the manitoba-maint pusher tries up to 3 restarts (10s / 30s / 60s back-off) before paging the operator. Usually it's back inside 2 minutes.

My stream got cut off mid-show #

The stack enforces a hard 4-concurrent-stream cap per member — not a total across the whole server. If you personally opened a 5th stream at the same time, the kill-stream cron ends one of your own streams within 60 seconds; it never touches other members' streams. If your stream was cut and you weren't running 5 of your own, that's a different issue — talk to the operator.

4Books, comics, audiobooks

These shelves were retired on 2026-08-16.

What happened to the books, comics and audiobooks? #

Retired 2026-08-16. The four reader apps that served the printed and spoken shelves were shut down and removed. They had no readers — the shelves were empty — so the operator retired them rather than keep four unused services patched, monitored and paged on.

Nothing you were using went away with them: video (movies, TV, anime) is untouched, and Plex, Seerr and the dashboard all work exactly as before. The nightly job that pruned the text shelves is gone too, along with the four monitors that watched the apps.

If you would like ebooks, comics, manga or audiobooks back on QFlix, say so — it is a question of demand, not of capability, and the operator will happily stand a reader back up if anyone actually wants one.

5Newsletter

The weekly Plex digest.

What is the Monday newsletter and how do I subscribe? #

Every Monday at 08:00 America/Phoenix (15:00 UTC, right after the maintenance window closes) a Python job (qflix-newsletter) renders a digest of what's new in Plex, what's on deck for the next two weeks, and a “Behind the scenes” recap of what changed under the hood that week — and emails it via Listmonk.

Subscribers are pulled from two places automatically: your Plex friends list and Seerr users. If you're in either, you're already subscribed. Unsubscribe link at the bottom of every email — that's standard Listmonk and works instantly.

Email sections: Pick of Week → New Movies → New TV → New Anime → Coming Soon → Behind the scenes → Nerd Corner.

I didn't get this week's email #

  • Check spam — first send to a new address often lands there.
  • Confirm the email on file. The operator can look you up in Listmonk.
  • If GitHub was unreachable that week, the “Behind the scenes” section just doesn't appear; the rest of the email still sends.
  • If the maintenance window over-ran, the Monday 08:00 trigger fires anyway — it doesn't wait.

6Why things disappear

QFlix is a self-pruning library — here's the rules.

Something I watched is gone — what gives? #

QFlix runs qflix-reaper on a daily timer. The rule on movies is roughly: if you watched it ≥ 60 days ago and nobody else has watched it, it gets removed (from Plex and from disk). This keeps the disk usable on a shared seedbox. The reaper runs with caps (max 50 items / 30% per library) and writes an audit manifest before every deletion run.

Re-request via Seerr and it'll be re-grabbed. The 60-day clock restarts.

Want a title preserved? The operator can pin items to skip the reaper rule. Just ask.

An ebook / audiobook I had is gone #

A separate nightly job used to trim anything in the ebook / audiobook / comic / manga shelves that hadn't been touched in 365 days. Both the job and the shelves themselves were retired on 2026-08-16 — see the books question.

7SSH tunnel & admin

For the operator. Public surfaces are HTTPS; admin surfaces require the tunnel.

How does the SSH tunnel work? #

scripts/manitoba-tunnel.ps1 is a PowerShell daemon registered as a Windows scheduled task (\Archangel\Manitoba SSH Tunnel). It mirrors workstation local-port → server-port so bookmarks read naturally — localhost:17026/sonarr/ on your machine = Sonarr on the seedbox.

Default forwards:

sonarr 17026   | sonarr2 17003   | radarr 17027    | radarr2 17008
prowlarr 17024 | bazarr 17031    | bazarr2 17032   | tautulli 17014
qbittorrent 17041 | listmonk 42014 | uptime-kuma 42005 | tdarr 42018
Why ExitOnForwardFailure=no? A stopped service shouldn't kill the whole tunnel. The poll target is port 42014 (Listmonk, always-on systemd).

I can't reach localhost:17026 — tunnel down? #

  1. Win+R → taskschd.msc → look for \Archangel\Manitoba SSH Tunnel. Is it running?
  2. From PowerShell: Test-NetConnection localhost -Port 42014 — Listmonk is the always-on canary.
  3. If the task is running but the port test fails: kill it and re-run. SSH multiplexing can wedge after long sleeps.
  4. If the task isn't running: schtasks /Run /TN "\Archangel\Manitoba SSH Tunnel".
FQDN gotcha: the script is gitignored because it hardcodes the real FQDN. If you cloned QFlix fresh, re-create it with your operator slot's host.

Smoke test says “Could not resolve seedbox.example.com” #

The repo uses seedbox.example.com as a sanitized placeholder. Operator-local clones need both:

  • secrets/seedbox.host — the public HTTPS FQDN (operator slot, e.g. quadstronaut.seedbox.example.com).
  • secrets/seedbox.ssh-host — the SSH FQDN, which on Ultra.cc shared boxes is the shared hostname (e.g. seedbox.example.com), not the slot subdomain.

If you only set one, smoke + canaries will fail on whichever the other was needed for. Both lines, single-line files, no trailing newline.

8Maintenance window

Mondays, 11:00–15:00 UTC (04:00–08:00 America/Phoenix). The only time the stack is allowed to break itself.

What happens during the window? #

  1. Posts “window open” to Discord.
  2. Grabs ~/.opt/maint/window.lock (a watchdog at 17:00 CEST clears any stale lock).
  3. Runs Recyclarr (TRaSH-Guide sync), Kometa (collections / posters), Buildarr (declarative *arr config).
  4. Runs the UCC app-upgrade sweep as a step inside the window: app-<name> upgrade sequentially for every installed UCC app (replaces the previous Playwright clicker as of 2026-05-13); in-place tarball/zip swap for non-UCC systemd apps. (The old fixed-11:30-UTC timer was retired 2026-06-28 and folded into this orchestrator run.)
  5. Restores prior service state from the discovery snapshot.
  6. Releases the lock + posts “window closed” with a summary.

Pusher auto-heal is paused for the window so restarts don't race the upgrade sweep.

Why do upgradinatorr and the newsletter fire outside the window? #

  • upgradinatorr.timer fires Sun 06:00 — pre-window stale-grab re-search, so by Monday the *arr stack is already chasing fresh releases (good for the post-window cleanup pass).
  • qflix-newsletter.timer fires Mon 08:00 — post-window so the digest reflects whatever the window just upgraded.

The window started but never closed #

The watchdog timer fires at Mon 17:00 and clears stale ~/.opt/maint/window.lock. If you arrive Monday afternoon and the lock is still held, either:

  • Wait until 17:00 — the watchdog will clear it.
  • Manually: rm ~/.opt/maint/window.lock and post to Discord that you did it.

Don't kill manitoba-maint-window.service mid-run unless you're sure app-upgrade-all.sh isn't actively mid-upgrade — UCC's docker-based upgrades are safe to interrupt but mid-flight installers are annoying to clean up.

9Manifest & new apps

The manifest is the only place that records “what apps exist”.

How do I add a new app? #

  1. Add an entry to manifest/apps.yaml. Pick a class: ucc (managed by app-<slug>), systemd, cron, or library.
  2. Pick a health probe kind: http_api, http_root, systemd_only, port_listen, import_check, or process_pattern.
  3. Validate: ~/bin/manitoba-maint manifest validate.
  4. Create the Kuma monitor: ~/bin/manitoba-maint kuma audit reports missing monitors; the bootstrap script creates them and writes the push-token into secrets/kuma-push-tokens.json. The bootstrap also seeds the tokens dict from any existing file before writing, so manually-placed keys (e.g. for the workstation collector's external PUSH monitor) survive across runs — this self-heal landed 2026-05-22 after a token rotation silently broke the hourly workstation push.
  5. Wire notifications: every new monitor must attach to both Mission Control - QFlix (Discord) and Manitoba auto-heal webhook. The bootstrap script does the SQL INSERT INTO monitor_notification dance.
  6. Restart pusher: systemctl --user restart manitoba-maint-pusher.
Probe-kind cheat sheet

http_api — for *arr-style apps with an X-Api-Key header. Needs port_secret, auth_secret, path_template, optional urlbase_secret.

http_root — plain GET to / on a port. Optional hostname override for Docker-bridge-only services (e.g. FlareSolverr at 172.17.0.1:17011).

systemd_only — just checks the systemd unit is active (running).

port_listen — TCP connect to localhost:<port>.

import_check — for Python libraries: venv_python -c "import X". Tilde-expanded.

process_pattern — pgrep-backed; for raw processes like unpackerr or the Postgres checkpointer subprocess.

How do I remove an app? #

  1. Stop it: app-<slug> stop (or systemctl --user stop <unit>).
  2. Uninstall (UCC backs up to ~/.apps/backup/ automatically): app-<slug> uninstall.
  3. Remove the manifest entry from manifest/apps.yaml.
  4. Move related secrets into a dated quarantine: mv ~/secrets/<slug>.* ~/.purged-$(date +%F)/ (reversible).
  5. Delete the Kuma monitor + push token: SQL delete from monitor, then prune the entry from secrets/kuma-push-tokens.json.
  6. Remove the nginx fragment: rm ~/.apps/nginx/proxy.d/<slug>.conf; app-nginx reload.
  7. Restart pusher; smoke; commit the manifest change.
Don't rm -rf directly — always move to ~/.purged-YYYY-MM-DD/ first. The 2026-05-10 purges all kept dated quarantine dirs and that has paid off twice already.

10Kuma & canaries

Push monitors, status page, and the 33 end-to-end canaries.

Why is auto-heal in the pusher and not in a Kuma webhook? #

Kuma runs in an isolated network namespace on Ultra.cc and cannot reach the host loopback. That's why the pusher pushes status TO Kuma every 60 s, and the pusher itself fires the auto-heal (recovery.trigger_async) after 3 consecutive failed probes — not Kuma.

Kuma's role is visibility (status page + Discord) and the public alert side. The actual healing decision is in scripts/maint/lib/recovery.py.

canary-dash-asset-integrityevery 15 minThe deployed dashboard can actually hydrate. Two predicates: every /_app/immutable/* asset the served shell references must resolve 200 from the process that served the shell, and the document's advertised Content-Length must match the bytes actually delivered. Added after the board served a dead shell for ~22 h with every monitor green — a new build/ was shipped over a live node process, and adapter-node's sirv snapshots its static-file manifest once at start, so 6 of 10 referenced modules 404'd while the files sat on disk and rewritten files kept advertising their old byte count (ERR_CONTENT_LENGTH_MISMATCH). A third predicate catches a 200 whose body never arrives at all, which satisfies neither of the other two. Never restarts when the files are genuinely missing (a partial deploy), when a stalled body suggests a wedged worker, or when a single dropped response fails to reproduce on an immediate re-check.

Each canary pushes a status to Kuma. If Kuma goes red, the operator gets pinged. If a canary's underlying script crashes (vs. silently returning OK), journalctl --user -u manitoba-maint-canary-<name>.service has the traceback.

I deleted a Kuma monitor in SQL — it's still showing on the status page #

Kuma 2.x caches monitors in memory. SQL DELETE while Kuma is running diverges the DB from the in-memory cache, and the deleted monitor will linger until restart.

  1. app-uptimekuma restart
  2. Wait ≥ 10 s for the in-memory cache to rebuild.
  3. For push monitors only: ~/bin/manitoba-maint canary push <name> once per monitor — the /metrics Prometheus endpoint filters by post-restart heartbeats, so until each canary has pushed at least once, audits show drift.

I set a notification channel as default but new monitors aren't using it #

Kuma's isDefault=true applies on UI-created monitors at creation time only. For monitors created via the bootstrap script (or any script-driven path), you must explicitly INSERT INTO monitor_notification for each (monitor_id, notification_id) pair. The bootstrap helper does this.

What does the production smoke actually check? #

scripts/smoke-test.sh runs ~50 assertions in five buckets. A clean run means everything from indexers through subscriber email is reachable. A single failure is operator-actionable — rerun after every tracked change.

11The *arr stack

Sonarr / Sonarr2 / Radarr / Radarr2 / Prowlarr / Bazarr / Bazarr 2 / FlareSolverr.

Why two Sonarrs and two Radarrs? #

Release naming for anime is different enough from western TV / film that mixing them confuses the quality profiles and the renamer. So each is split by release-naming convention, not by genre:

  • Sonarr / Radarr — cinema-style releases (English subs baked into release name, Scene / P2P naming).
  • Sonarr2 / Radarr2 — anime-style (group brackets, episode numbering, etc.). Configured with anime-specific Prowlarr indexers and TRaSH anime profiles via Recyclarr.

An indexer is returning 403 / Cloudflare-walled #

Prowlarr is configured to route Cloudflare-protected indexers through FlareSolverr. FlareSolverr listens on 172.17.0.1:<flaresolverr.port> (Docker bridge), not host loopback.

  • Verify FlareSolverr is up: Kuma monitor “FlareSolverr” pushes every 60 s. If red, pusher will restart up to 3 times.
  • Verify Prowlarr points at it: Settings → Indexers → FlareSolverr → URL should be http://172.17.0.1:17011 (use the real port from secrets/flaresolverr.port).
  • Smoke test: scripts/smoke-test.sh step 1 asserts ≥ 5 indexers + a search round-trip works.

Sonarr / Radarr queue is stuck on Importing #

A cron at :15 hourly runs arr-housekeeping.py --unstick which forces re-import on items wedged in the queue. If you can't wait, run it manually: 

~/bin/manitoba-maint arr-housekeeping unstick

Common root cause: qBittorrent finished but didn't fire the “Run external program on completion” — check qBit Preferences → Downloads → External program is configured.

Recyclarr vs Buildarr vs Kometa — what does each do? #

Buildarrdaily 04:30 in-windowDeclarative buildarr.yml → reconciles every other *arr setting (indexer list, download client, notifications, custom formats)

If a quality profile mysteriously reverts, it's Recyclarr or Buildarr undoing your manual change at the next window. Edit the YAML, not the *arr UI.

I added an indexer in Prowlarr but Sonarr/Radarr don't see it #

Prowlarr pushes indexers to the *arrs via Apps → Sync App Indexers. Click that, or wait for the next scheduled sync (15 min by default). If the new indexer didn't appear in the *arr after the sync, double-check the App entry in Prowlarr points at the correct URL + API key.

12qBittorrent

The download client. Most failures here look like “stuck” or “not seeding”.

A torrent has been stuck at 0% / “Downloading metadata” forever #

  • Dead torrent. No seeders left. The *arr will mark it failed and grab the next release at the next re-search. Or remove it manually and force a re-search in Sonarr/Radarr.
  • Tracker dead / firewalled. Check the tracker's status page. Private trackers will sometimes go down for hours.
  • Disk full. See § 13 below.

Ratio is dropping on private trackers #

QFlix doesn't run cross-seed (yet). On private trackers, hardlinks preserve seeding while the file is in the Plex library — verify with smoke test step 5 (linkcount ≥ 2). If hardlinks aren't working, your seeding files get deleted after import and you bleed ratio. See § 13.

Imports aren't happening — qBit finishes but Sonarr does nothing #

qBit's Run external program on torrent completion setting must be configured to ping each *arr's /api/v3/command. If you nuked qBit config or did a fresh install, this resets and silently breaks imports.

Fix: qBit → Options → Downloads → Run external program on torrent completion should call ~/bin/post-import.sh "%F" "%L" "%N" (or whatever the post-import dispatcher is named in this repo).

13Files, hardlinks, disk

The shared seedbox runs on someone else's filesystem rules. Respect them or pay the disk-bill.

Why hardlinks matter so much #

Hardlinks let one file exist at two paths with the same inode — one copy on disk, two filenames. The *arr stack uses this to import torrents into the Plex library without duplicating the file: qBittorrent keeps seeding from ~/data/torrents/ while Plex sees the same bytes at ~/data/media/.

If hardlinks break (e.g., torrents and media end up on different mountpoints), the *arr quietly falls back to copy — doubling the disk usage and breaking seeding when qflix-reaper later deletes the Plex copy.

Smoke test step 5 spot-checks linkcount ≥ 2 on a sample of Movies. If that fails, fix the *arr download client config so the import path is on the same mountpoint as the torrent path.

The seedbox is full / over quota #

  1. Check: df -h ~ on the seedbox.
  2. Trigger qflix-reaper immediately (dry-run first, then execute): python3 ~/scripts/maint/qflix-reaper.py to preview, then python3 ~/scripts/maint/qflix-reaper.py --execute --json to delete. The quota canary at 90% disk fires this automatically.
  3. Manually purge old ~/.purged-YYYY-MM-DD/ quarantine dirs that have aged out.
  4. Check qBit for completed torrents past their seed ratio that you can remove.
  5. Remove the lowest-ratio completed torrents directly in the qBittorrent WebUI (sort completed by ratio, right-click → Delete with data). There is no scripted auto-trim — this is a manual operator action.
Hard limit: on Ultra.cc, the user slot has a quota. Hit it and writes start failing silently — imports stop, Plex transcodes start dying mid-stream. Watch scripts/smoke-test.sh step 6 for “disk usage” alerts.

Is there a backup? #

No. Ultra.cc shared seedboxes are not backed up by the provider. Media is considered ephemeral — if a drive dies, the *arr stack re-downloads everything. The only state worth caring about is in ~/.apps/<app>/data/ dirs (per-app SQLite DBs) and ~/secrets/.

The ~/.purged-YYYY-MM-DD/ convention is the only “backup” for in-flight deletions. Keep them around for at least 30 days before final removal.

14Tdarr transcoding

Background re-encode to keep file sizes sane.

Why is Tdarr pinned to v2.17.01? #

Tdarr > 2.17.x requires a newer GLIBC than what's installed on the Ultra.cc base image. Upgrading would break the binary. Pinned via versions.env → TDARR_VERSION=2.17.01 with max_reason: "GLIBC blocker". The maintenance window upgrader respects the pin.

Tdarr queue isn't moving #

  • Verify the node service is up: systemctl --user status tdarr-node.service. Heartbeat cron restarts on inactive.
  • Verify the node is connected to the server in the Tdarr UI (localhost:42018/tdarr via tunnel).
  • If both are up but queue is empty: Tdarr scan hasn't picked up new files. Tdarr → Libraries → Scan / Run.

16Top 10 screw-ups

The recurring own-goals. Memorize these.

1. Forgetting to expand “Advanced” on Seerr anime requests #

The anime servers are non-default. Files end up in the wrong library if you click Request without picking the Anime server. See § 2.

2. Assuming a wedged SSH tunnel will self-heal #

It won't always. ExitOnForwardFailure=no means failed forwards just stay broken — the daemon keeps trying but the existing wedged session blocks. Solution: kill the scheduled task, re-run it. See § 7.

3. Letting hardlinks silently break #

Torrents and media on different mountpoints → *arr copies instead of links → double disk usage + private-tracker ratio death. Smoke step 5 catches it; act on the failure immediately.

4. Claiming “X is parked / removed” without verifying live state #

The 2026-05-10 Maintainerr false-park incident: a stale comment said Maintainerr was “intentionally parked”; it had been running fine for weeks. Verify against the seedbox before writing any “not running” claim. inventory.md is the source of truth. (Maintainerr itself was subsequently decommissioned 2026-06-20 and replaced by qflix-reaper — the lesson stands regardless of which app is in scope.)

5. Probing a service immediately after restart #

After app-X restart, the process exits and re-launches but the port rebind takes a few seconds. Sleep ≥ 10 s before the first probe, especially for Docker-class services (Seerr).

6. Editing Kuma SQL while Kuma is running #

Kuma caches monitors in memory. SQL DELETE + no restart = phantom monitor on the status page. Always restart after schema edits. See § 10.

7. Assuming isDefault=true auto-attaches to new monitors #

It doesn't, for script-created monitors. Always explicit-INSERT into monitor_notification. See § 10.

8. Subprocess in Python doesn't expand ~ #

The Q2 import_check probe crashed for weeks because subprocess.run(["~/.apps/python-plexapi/venv/bin/python", ...]) doesn't tilde-expand. Always os.path.expanduser() first.

9. Probing a Docker-bridge service on 127.0.0.1 #

FlareSolverr binds 172.17.0.1:17011, not loopback. Use the hostname override on the manifest health probe. The health probe now supports this; remember to set it.

10. New public path returning 401 Unauthorized #

The outer Ultra.cc nginx applies htpasswd by default. To make a path public, the proxy.d fragment must include auth_basic off;. Listmonk, Tautulli, and Seerr all rely on this. Without it, end-users hit a basic-auth dialog they don't have credentials for.

17Emergency playbook

If something is on fire right now.

Plex is down and the auto-heal didn't fix it #

  1. SSH to seedbox.
  2. app-plex status — is it actually stopped, or just unreachable?
  3. app-plex restart. Wait 30 s.
  4. Probe: curl -sI -o /dev/null -w '%{http_code}\n' http://localhost:32400/web/ → should be 401 (auth wall, but server up).
  5. If still failing: journalctl --user -u plex.service -n 80. Common: storage path missing (mount failed), claim token expired (re-claim in cp.ultra.cc).
  6. Force a pusher recompute: systemctl --user restart manitoba-maint-pusher.

The disk is full #

See § 13. Sequence: df -h → run qflix-reaper (python3 ~/scripts/maint/qflix-reaper.py --execute --json) → purge oldest ~/.purged-* → qBit cleanup → re-check.

Multiple monitors red, can't tell what's the root cause #

  1. Check ~/.opt/maint/state.json for the pusher's latest failure log.
  2. journalctl --user -u manitoba-maint-pusher -n 200 — look for the first failure (a downstream often cascades).
  3. Common root cause: nginx down (everything 502), Postgres down (Listmonk red), seedbox over quota (everything write-fails).
  4. Get nginx up first: app-nginx restart.
  5. Then disk: df -h.
  6. Then per-app: ~/bin/manitoba-maint kuma audit to see the current red list.

The Monday window broke something — how do I roll back? #

  1. Identify the upgraded app: journalctl --user -u manitoba-maint-window.service -n 200.
  2. UCC apps have a backup at ~/.apps/backup/<slug>-<old-version>.tar.gz.
  3. app-<slug> stop; tar -xzf ~/.apps/backup/<slug>-... -C ~/.apps/; app-<slug> start.
  4. Pin the version in versions.env with a max_reason so it doesn't re-upgrade next week.
  5. Commit the pin to git.

18Nerd Corner — the tech stack

Every app in QFlix is somebody's open-source project. Here's the tech behind the curtain.

The .NET wing — Sonarr, Radarr, Prowlarr, Bazarr, Recyclarr #

The whole *arr family is C# / ASP.NET Core. For years they ran on Mono on Linux because .NET wasn't cross-platform yet — that's why old install guides still talk about mono-complete. Sonarr v4 (2023) and Radarr v5 finally cut Mono and ship native .NET 6+ runtimes. Saves a lot of memory and one entire dependency layer.

Recyclarr is also C# / .NET — it just speaks to the *arr APIs to apply TRaSH-Guide profiles in bulk.

The Python wing — Tautulli, Kometa, Buildarr, FlareSolverr, qflix-newsletter #

Tautulli is Flask-based; it's the original community Plex stats dashboard, around since the PlexPy days. Kometa (formerly Plex Meta Manager) is a YAML-driven Python pipeline that turns config files into Plex collections + posters. Buildarr is “Infrastructure-as-Code for *arrs” — declarative YAML in, reconciled *arr settings out (think Terraform, but for Sonarr).

FlareSolverr drives a headless browser (Selenium / undetected-chromedriver) to solve Cloudflare challenges Prowlarr can't pass on its own. qflix-newsletter is bespoke — Python + Jinja2 templates + the Listmonk REST API, ~600 LoC total.

The Node.js wing — Uptime Kuma, Tdarr, Seerr, qflix-dash #

Uptime Kuma is by Louis Lam — started as a personal Hong Kong side-project and became the de-facto self-hosted status page (think open-source UptimeRobot). Maintainerr (NestJS + React) was the former 60-day retention engine — it stepped in after Deleterr was abandoned but was itself decommissioned 2026-06-20 after a Plex-ID resolution bug made its deletes unfixable. The 60-day retention rule is now handled by qflix-reaper (scripts/maint/qflix-reaper.py), a bespoke Python script on a daily systemd timer.

Tdarr wraps FFmpeg with a Node orchestrator and a worker-node model (“servers” + “nodes”). Seerr (the Overseerr / Jellyseerr family) is Next.js + TypeScript. qflix-dash — SvelteKit on the Node adapter — is the dashboard you see at the QFlix root URL. (It replaced Homarr, a Next.js board that was retired in 2026.)

The Go wing — Listmonk, unpackerr #

Listmonk is by Kailash Nadh, CTO of Zerodha (India's largest stockbroker, written largely in Go and CommonLisp). It's a single-binary newsletter platform — Postgres for storage, Mailchimp-class features, zero JVM/Python overhead. QFlix uses it for SMTP fan-out on the Monday digest.

unpackerr is by golift — one tiny binary that watches *arr download directories and unrar's archives so qBittorrent and the *arrs don't have to. Runs as a long-lived systemd unit and never makes news, which is the highest praise for an unpacker.

The C / C++ wing — qBittorrent, Plex, Nginx, Postgres, systemd #

qBittorrent is C++ / Qt — the spiritual open-source successor to µTorrent. The moment µTorrent went ad-supported in 2012, qBit picked up the torch and never looked back. Plex Media Server is mostly C/C++ with Python plugins; its lineage traces back through OSXBMC (2008) to XBMC, the original Xbox Media Center.

The boring-but-essential stack underneath: nginx (Igor Sysoev, 2004) does HTTPS termination + reverse-proxy with QFlix's proxy.d fragments. PostgreSQL (1996 — older than half the apps it supports) holds Listmonk subscriber data. systemd (Lennart Poettering, 2010) runs every long-lived service as a user-unit; QFlix had 57 services + 55 timers under ~/.config/systemd/user/ as of 2026-07-30 (the exact count keeps climbing as new janitors and canaries ship, so treat this as a snapshot, not a spec).

The automation glue — UCC app-* CLI, systemd timers, mermaid, bash #

UCC app-* CLI. Every UCC-managed app exposes an app-<name> command with an upgrade subcommand. The weekly sweep (scripts/maint/app-upgrade-all.sh) walks ~/.apps/*/, calls app-<name> upgrade sequentially, and falls through a default skip list (postgres, mariadb, nginx, openvpn, tailscale, wireguard). Replaced the earlier Playwright-on-cp.ultra.cc clicker on 2026-05-13 — the CLI path is faster, has no browser dependency, and removes the AngularJS selector fragility.

systemd user timers (not cron) for everything window-related, because timers handle missed runs gracefully across reboots. cron still runs a few simple hourly/nightly heartbeats. mermaid.js renders the diagrams in the README without any build step. bash for ~70% of the install / configure / smoke scripts — install scripts in scripts/configure/ are numbered for execution order.

The AI bit that was — Google Gemini (retired), TMDB #

The Monday newsletter used to run an AI Picks section that called Google Gemini with a prompt like “here's what's in the library and what was recently added — recommend three under-watched titles in the ‘if you liked X, try Y’ format.” Gemini's free tier started returning 429 limit:0 on every run, so the section was retired 2026-06-27 and replaced by the “Behind the scenes” recap. That recap is written each week by a scheduled Claude cloud routine — a warm, plain-English summary of what improved — with an automatic fallback to a plain list of that week's GitHub commits if the routine doesn't run (see “What is the Monday newsletter” above). So there's still a touch of AI in the newsletter, just a more useful one.

TMDB (The Movie Database, community-driven, 2008) is the canonical metadata source for everything visual — Seerr searches against it, Sonarr / Radarr enrich grabs with it, the newsletter pulls thumbnails from its image CDN. Free for non-commercial use, and the data quality genuinely embarrasses some commercial alternatives.

The community — TRaSH-Guides, the *arr Discord, the Selfhosted subreddit #

None of this works without the operator-volunteer ecosystem behind it: TRaSH-Guides (trash-guides.info) is a single-maintainer-plus-contributors documentation site that has become the canonical source of *arr quality-profile JSON; Recyclarr just consumes it. r/selfhosted + the various *arr Discords are where 90% of the “why did this break” answers live. QFlix's design mostly follows their hard-won conventions — deviating costs a lot of debugging time.
